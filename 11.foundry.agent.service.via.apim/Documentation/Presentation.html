What changes in the C# code

Removed
AzureCliCredential passed straight to AIProjectClient
Endpoint pointing at the Foundry resource directly
Added
Endpoint now points at the APIM gateway URL
A raw HttpClient with an ApiKeyAuthenticationPolicy injecting the APIM api-key header

Fixes in APIM

A couple of things the Foundry link didn't set up

The backend itself was already created by the Foundry link — but the API's policy still needed to reference it explicitly:

<policies>
    <inbound>
        <base />
        <set-backend-service backend-id="ms-blog-ai-samples-foundry" />
    </inbound>
    <backend><base /></backend>
    <outbound><base /></outbound>
    <on-error><base /></on-error>
</policies>
Fixes in APIM

App Insights logging had to be turned on explicitly

Headers and payload logging aren't on by default — without this, requests would be logged but the custom headers wouldn't be captured.

Observability

Requests and dependencies, both logged centrally

App Insights tableSourceCustom headers visible?
requestsAPIMYes — every request to APIM
dependenciesFoundryOnly on the initial POST — not on downstream agent/tool spans
You will not see custom headers inside Foundry itself. You'll see them on the requests row in APIM, and on the single dependencies row for the POST that triggered the agent — but not on the subsequent agent/tool telemetry that runs downstream and out of process.
Correlation

Linking a request to its downstream agent telemetry

Because custom headers don't propagate to the downstream agent/tool spans, correlating them means logging message bodies and joining on the response id: gen_ai.response.id on the dependency, matched to the response body's id on the request.

let ai_response_id = "resp_...";
union withsource=SourceTable requests, dependencies
| where parse_json(tostring(customDimensions["Response-Body"])).id == ai_response_id
    or customDimensions["gen_ai.response.id"] == ai_response_id
| extend
    Request_x_correlation_id_ = tostring(customDimensions["Request-x-correlation-id"]),
    gen_ai_agent_name_ = tostring(customDimensions["gen_ai.agent.name"]),
    ResponseBody = parse_json(tostring(customDimensions["Response-Body"]))
| extend total_tokens_ = tolong(ResponseBody.usage.total_tokens)
| project timestamp, SourceTable, Request_x_correlation_id_, gen_ai_agent_name_, total_tokens_
| order by timestamp desc
Simpler standalone queries for just requests or just dependencies (without the correlation join) are in this sample's Notes.md.
Outcome

Reflections after getting it working

What worked
The whole scenario works end to end — subscription key in, managed identity out, requests and dependencies both centrally logged
Centralizing observability this way is genuinely valuable
Still to think about
Body-logging to correlate by response id is more involved than ideal — an APIM policy that promotes the response id to a header would be cleaner
A standard header set may not fit every team — possibly multiple APIs per scenario, with some shared standards
Distributed correlation across processes needs more thought — flowing standard headers like traceparent / x-ms-correlation-id end to end
Net effect: worth the extra setup for the centralization it buys, but the correlation story between the gateway and the downstream agent telemetry still has rough edges to smooth out.
