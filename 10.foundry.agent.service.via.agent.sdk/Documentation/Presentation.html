What sample 10 demonstrates

Sample Family

A new axis: who owns the agent definition

05–09 · Hello World family
Agent instructions, model & tools defined in the app's own code
IChatClient (ME.AI) or AIAgent (MAF), optionally via APIM
Every variant still talks to a raw Azure OpenAI deployment

Agent created and versioned inside Azure AI Foundry, not in code
App just supplies a name + version via AgentReference
10 = direct to Foundry · 11 = same call routed through APIM
This is a different kind of change to the 05→09 series: instead of swapping SDKs or adding a gateway, the agent itself moves out of the codebase and into a managed Foundry resource.

Step 2

Calling the agent from C#

AIProjectClient projectClient = new(
    endpoint: new Uri(endpoint),
    tokenProvider: new AzureCliCredential());

// Points at an agent Foundry already knows about — no model,
// instructions or tools declared here at all.
AgentReference agentReference =
    new(name: agentName, version: agentVersion);

ProjectResponsesClient responseClient =
    projectClient.OpenAI.GetProjectResponsesClientForAgent(agentReference);

ResponseResult response =
    await responseClient.CreateResponseAsync(userPrompt);
Endpoint shape: https://<your-foundry>.services.ai.azure.com/api/projects/<your-project>. In production this would use DefaultAzureCredential so a deployed app picks up its managed identity; AzureCliCredential is used here for local dev.
Step 3 · Gotcha

Sending custom headers — they go nowhere useful

Custom headers can be added by wiring a raw HttpClient into the SDK's transport, and they do get sent on the wire. But calling Foundry directly means there's no intermediary logging the request — so those headers never show up anywhere in Application Insights.

Takeaway: without a gateway in front of Foundry, there's nowhere server-side to capture request-level metadata like a correlation id or customer id — that's the gap sample 11 exists to close.
