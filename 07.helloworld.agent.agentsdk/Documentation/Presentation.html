Overview

What sample 07 demonstrates

Goal
Build the exact same "hello world" agent as sample 05 — but using the Microsoft Agent Framework (Microsoft.Agents.AI v1.13.0) instead of raw Microsoft.Extensions.AI
Wire up the same three tools: GetCurrentDateTime, GetWeather, Calculate
Talk directly to Azure OpenAI (no APIM hop, unlike sample 06)
Compare how Application Insights telemetry looks when the tool-call loop is owned by MAF instead of explicit ME.AI middleware
Program.cs shape
Config → OTel setup → tools → build AIAgent → RunAsync() → flush
Key type
AIAgent created via .AsAIAgent(instructions, name, tools)
Entry point
agent.RunAsync(userPrompt) → AgentResponse

Diff · vs Sample 05

What changed since sample 05

Removed
The IChatClient builder pipeline (AsBuilder()...UseFunctionInvocation()...Build() as the final call site)
UseFunctionInvocation() middleware — no longer needed, MAF owns the loop
Manual List<ChatMessage> history with a ChatRole.System message
ChatOptions { Tools = [...], ToolMode = Auto } passed per call
response.Usage — token counts read straight off the call
Added
Microsoft.Agents.AI + Microsoft.Agents.AI.OpenAI NuGet packages
.AsIChatClient().AsBuilder()...Build().AsAIAgent(instructions, name, tools) — one agent object built once
System prompt moved to the instructions: parameter
Tools registered once at construction, not per call
agent.RunAsync(userPrompt) returning AgentResponse (still exposes .Usage in this MAF version, via .Text + .Usage)
Diff · vs Sample 06

What changed since sample 06

Sample 06 layered APIM routing on top of the sample 05 pattern. Sample 07 goes a different direction — same MAF swap as the sample 05 diff, but it drops the APIM hop entirely rather than combining both.

Removed (relative to 06)
Routing through Azure API Management
OpenAIClient + Ocp-Apim-Subscription-Key header on HttpClient
Dependency on an APIM inbound policy to inject the real api-key
UseFunctionInvocation() middleware (same removal as vs. sample 05)
Added (relative to 06)
AzureOpenAIClient talking directly to the Azure OpenAI endpoint
AIAgent / .AsAIAgent() from Microsoft Agent Framework
Config shape simplified — Endpoint is the Azure OpenAI resource URL, not an APIM gateway URL
Net effect: sample 07 changes two things sample 06 did not touch — the client library gateway (no APIM) and the agent abstraction (MAF instead of ME.AI). It is best read as "sample 05 rebuilt on MAF," not as a superset of sample 06.
Code Comparison

Building & running the agent — old vs new

Samples 05 / 06 · Microsoft.Extensions.AI
IChatClient chatClient =
  new AzureOpenAIClient(uri, key)
    .GetChatClient(deployment)
    .AsIChatClient()
    .AsBuilder()
    .UseFunctionInvocation()
    .UseOpenTelemetry(o => ...)
    .Build();

var messages = new List<ChatMessage>
{
  new(ChatRole.System, systemPrompt),
  new(ChatRole.User, userPrompt),
};
var options = new ChatOptions
{ Tools = [t1, t2, t3], ToolMode = Auto };

ChatResponse response = await chatClient
  .GetResponseAsync(messages, options);
Sample 07 · Microsoft Agent Framework
AIAgent agent =
  new AzureOpenAIClient(uri, key)
    .GetChatClient(deployment)
    .AsIChatClient()
    .AsBuilder()
    .UseOpenTelemetry(o => ...)
    .Build()
    .AsAIAgent(
      instructions: systemPrompt,
      name: "helloworld-agent-agentsdk",
      tools: [t1, t2, t3]);

// No message list, no ChatOptions,
// no UseFunctionInvocation() — MAF
// owns the tool-call loop internally.
AgentResponse r =
  await agent.RunAsync(userPrompt);

Observability

Application Insights — what stays the same

MAF wraps the OpenAI ChatClient as an IChatClient internally, so the same gen_ai.* semantic-convention spans and the Microsoft.Extensions.AI / Experimental.Microsoft.Extensions.AI activity sources are emitted regardless of which sample is running.

Telemetry aspect05 / 06 (ME.AI)07 (MAF)
Root span (run-ai-agent)Custom, ActivityKind.ServerSame pattern, still hand-added
Custom agent dependency spanAdded manually with gen_ai.agent.name tagsStill added manually — MAF does not set these tags on its own
gen_ai.client.token.usage metric✅ via ME.AI meter✅ same meter, MAF sits above it
Sensitive data captureEnableSensitiveData = trueSame flag, same behaviour
App Insights Agent Preview blade✅ with custom span✅ with the same custom span
Bottom line: switching to MAF does not change what you have to instrument by hand. The custom Invoke Hello World Agent span with gen_ai.agent.name / gen_ai.operation.name is still required in sample 07, exactly as it was in samples 05 and 06.
Takeaways

Why this sample exists

Use sample 07 as a reference when…
You want the shortest path to a working multi-tool Azure OpenAI agent (~150 lines)
You'd rather not hand-write the tool-call loop or manage message history yourself
You're evaluating Microsoft Agent Framework for a new project and want a like-for-like baseline against sample 05
You plan to grow into multi-agent orchestration later and want to start on the framework built for it
Still reach for sample 05 / 06 when…
You need per-call token usage or fine-grained control over the message list (05)
You need to route through APIM for governance, quota, or key rotation (06)
You're building a library others will consume and want the lowest-level, most composable API
See 08.Agents.SDK.Differences for the deeper framework-vs-framework comparison this sample is drawn from, and Documentation/ReadMe.Frameworks.md in this folder for the pros/cons written up in prose.
