Why This Matters

"Same thing twice" — until you write the first query

On the surface
Both products export OpenTelemetry
Both land in the same Application Insights resource
Both track model calls, tokens, tool use
In practice
Different primary table, different field naming, different identity model
Structurally different queries for the exact same question
Why it matters for dashboards
A dashboard built for one product's schema does not transfer to the other

1 · Table Choice

traces vs dependencies

Claude Code → traces
Every prompt, model call, tool decision is its own named log-style event
Discriminated by the native message column
claude_code.user_prompt
claude_code.api_request
claude_code.api_error
claude_code.tool_decision
claude_code.tool_result
claude_code.mcp_server_connection
GitHub Copilot → dependencies
One row per outbound call, distinguished by gen_ai.operation.name
Native columns Claude's rows don't have: duration, success, resultCode, performanceBucket
Copilot only touches traces for one thing — counting session starts (copilot_chat.session.start)
Why it matters: traces reads like an event log; dependencies reads like a call log. The same question ("how many tool calls failed today?") is a structurally different query in each product.
2 · Field Naming

Bespoke fields vs. an industry-standard convention

Claude Code — flat & bespoke
input_tokens, output_tokens, cost_usd, model, effort
Anthropic invented these names for Claude Code specifically
GitHub Copilot — OTEL GenAI semantic convention
gen_ai.usage.input_tokens, gen_ai.request.model, gen_ai.operation.name
Shared by many GenAI tools, not just Copilot
Real consequence: generic field names could collide with an unrelated GenAI tool's telemetry in the same App Insights resource. Every Copilot query in this app filters on instrumentationlibrary.name == "copilot-chat" (VS Code) or "github-copilot" (CLI) first, before touching any gen_ai.* field. Claude's bespoke naming doesn't need this guard.
3 · Identity & Privacy

Per-user reporting: possible for one, impossible for the other

Claude Code
Emits real user & org identity on every event: user.email, user.id, org.name
Enables a per-user leaderboard, an inactive-user ("waste") report, or an org-level rollup
GitHub Copilot
No per-user identity anywhere — not a blank field, an absent one
Every Copilot dashboard is necessarily workspace- or session-scoped, never per-user
Worth calling out explicitly in a presentation: someone will ask "can we see which developer is using the most tokens?" — the honest answer for GitHub Copilot's default telemetry is no. That's a hard constraint baked into the data, not a feature we chose not to build.
4 · Prompt & Session Correlation

Reconstructing "the story of one request"

Claude Code — designed sequence
Every user prompt gets a durable prompt.id
Every related event (model request, tool decisions/results, API error) carries the same prompt.id, ordered by explicit event.sequence
session.id groups many prompts into one session
traces
| extend prompt_id_ = tostring(customDimensions.["prompt.id"])
| where prompt_id_ == '<id>'
| order by toint(customDimensions.["event.sequence"]) asc
GitHub Copilot — flatter correlation
No "prompt" concept or ordered event chain
Closest equivalent: chat_session_id (VS Code) or conversation.id (CLI)
Rows tied together mostly by timestamp, not an explicit sequence number
Aside: neither product uses App Insights' native operation_Id for this — both roll their own correlation key in customDimensions.
5 · Prompt Text Capture

A direct field read vs. a regex extraction

Claude Code
Prompt text lives in its own clean field
customDimensions.prompt
// on the claude_code.user_prompt event
GitHub Copilot
Prompt text lives inside copilot_chat.user_request, wrapped in hundreds of lines of injected workspace context
tostring(customDimensions.["copilot_chat.user_request"])
// then regex-extract <userRequest>...</userRequest>
// the raw field is not display-ready
One of the more surprising differences in practice — the same "what did the user ask?" question is a direct field read for Claude and a regex extraction for Copilot.

Claude Code's cost_usd is a genuine differentiator — cost reporting is a straight sum(). GitHub Copilot emits no cost field; any cost figure has to be estimated externally from token counts and a rate card, and GitHub doesn't publish per-token Copilot pricing the way OpenAI/Anthropic publish API pricing — so a Copilot cost estimate is inherently softer.
7 · Tool & Sub-Agent Usage

One tool call, two events vs. one row

Claude Code
tool_decision — how the call was authorized (decision.source: auto-approved, user-approved, rejected)
tool_result — whether it succeeded
A real governance signal: "how often do users have to manually approve a tool call?" is a first-class query
Sub-feature: skill.name identifies which Claude Skill ran
GitHub Copilot
Single execute_tool row with gen_ai.tool.name and a native success bool
No approval/decision concept — Copilot's tool-use model has no comparable per-call authorization step
Sub-feature: gen_ai.agent.name — "GitHub Copilot Chat" (main chat), "title" (auto-title), "XtabProvider" (Next Edit Suggestions), "panel/editAgent" (inline edit)
8 & 9 · Client Sources & Error Telemetry

Two clients to filter, one missing error event

GitHub Copilot — two clients, same shape
VS Code extension: instrumentationlibrary.name == "copilot-chat"
Copilot CLI: "github-copilot"
Forgetting either filter is the easiest way to silently under-count usage
No dedicated error event — reliability is inferred from success == false, or the generic (unconfirmed) exceptions table
Claude Code — one surface
No client split in the same way — one product surface
terminal.type / service.name describe the environment (which IDE, which terminal), not separate applications
Dedicated claude_code.api_error event — "show me recent errors" is a direct query
Practical Takeaways

What this means for dashboards & reporting

Both schemas need injection-style escaping — prompt text, tool arguments, session/conversation IDs are client-emitted content, not trusted input, before they're interpolated into a follow-up KQL query
Always scope GitHub Copilot queries by instrumentationlibrary.name before touching any gen_ai.* field — those names are a shared industry convention, not Copilot-exclusive
Claude Code's flat fields are simpler to query today, but track one vendor's naming choices that could change without notice; Copilot's OTEL GenAI convention is more likely to stay portable, at the cost of shallower per-product detail
If per-user or per-org reporting is a requirement, Claude Code is the one of the two that supports it today — Copilot's default export has no per-user identity to report against, full stop
