Architecture Overview

One request, five hops

Claude Code (.mcp.json, OAuth client)
        │
        │ 1. GET /.well-known/oauth-protected-resource/pipedrive-copilot-mcp-server/mcp
        │ 2. GET  {authorization_servers}/.well-known/openid-configuration
        │ 3. GET  /oauth-proxy/authorize   (redirect, resource param stripped)
        │ 4. POST /oauth-proxy/token       (code exchange, resource param stripped)
        │ 5. POST /pipedrive-mcp-server/mcp   (Authorization: Bearer <token>)
        ▼
Azure API Management — api-kv-sales-marketing
  ├─ oauth-proxy                              (Entra OAuth proxy)
  ├─ well-known-oauth-protected-resource       (RFC 9728 metadata)
  ├─ pipedrive-mcp-server (type: mcp)  (validates token, exposes tools)
  └─ pipedrive-api            (backend REST API, per-tool policies)
        │
        ▼
Azure Function App: pipedrive-api-helper  (calls the real Pipedrive API)
Steps 1–4 are pure OAuth discovery and login — they happen once (or on token refresh). Step 5 is every actual tool call, and it's the only hop that touches real data.

Who's the client, who's the backend

Once Claude Code holds a bearer token, it calls the MCP tool endpoints directly — both the token (Entra-issued) and an Ocp-Apim-Subscription-Key header are required. The subscription key is an optional second layer; Entra is the real security boundary.
The Problem

Auth happens with Entra, but MCP is hosted in APIM

MCP clients query the RFC 9728 discovery document unconditionally — if it 404s, some clients don't fail cleanly, they silently retry discovery forever and never attempt the real call
The resource field must exactly equal the URL the client is calling (its own origin + path) — clients validate this themselves and reject any deviation, including pointing it at the Entra app identifier instead
authorization_servers must point at a proxy in front of Entra, not at login.microsoftonline.com directly — otherwise the client tries to authorize against a domain that doesn't own the resource it's calling
The fix isn't "authenticate with Entra instead of APIM" — it's building two small proxy APIs inside APIM so that, from the client's point of view, discovery, login, and the MCP call all appear to come from the same origin.
Workaround · 1 of 2

The RFC 9728 discovery document

New APIM API
Path .well-known/oauth-protected-resource
One wildcard operation GET /{*resourcePath}, no real backend needed
One instance serves every MCP server on the same APIM — build it once
string resourcePath = (string)context
  .Request.MatchedParameters["resourcePath"];
string gatewayOrigin = "https://"
  + context.Request.OriginalUrl.Host;
return new JObject(
  new JProperty("resource",
    gatewayOrigin + "/" + resourcePath),
  new JProperty("authorization_servers",
    new JArray(gatewayOrigin + "/oauth-proxy")),
  new JProperty("bearer_methods_supported",
    new JArray("header"))
).ToString();

The Entra OAuth proxy

OperationRouteJob
DiscoveryGET /.well-known/openid-configurationFetch Entra's real discovery doc, rewrite authorization_endpoint & token_endpoint to point at this proxy
AuthorizeGET /authorize302 to Entra's real /authorize, stripping resource
TokenPOST /tokenForward to Entra's real /token, stripping resource from the form body
Gotcha: the scope query parameter needs its + characters replaced with real spaces before forwarding — query strings don't treat + as space the way form bodies do. Skip it and a second scope makes Entra reject the whole request with AADSTS65005. Same logic strips resource from both the authorization_code and refresh_token grants in /token.
1 · Entra ID App Registration

One public client, shared by every MCP server

PropertyValue
Sign-in audienceAzureADMyOrg (single tenant)
Public client fallbacktrue — required for PKCE with no client secret
Redirect URIs (Mobile and desktop apps)http://localhost:8080/callback, http://localhost
API permissionsMicrosoft Graph User.Read (delegated)
Gotcha — must be a public client: skipping this produces AADSTS7000218: The request body must contain the following parameter: 'client_assertion' or 'client_secret', which reads nothing like a "public client" problem. Not reliably settable via az ad app update — set isFallbackPublicClient: true via a Graph PATCH instead. Also: register the redirect URI under Mobile and desktop applications, not SPA — SPA uses a stricter, short-lived refresh-token model that breaks a CLI client.
2 & 3 · App Roles & Enterprise App

Define the role, then remember to assign it

App roles
One app role per permission group, e.g. mcp.myapp.read
Authorization downstream is checked against the roles claim on the token
Enterprise app — assign the role
Being able to sign in is a separate thing from holding the role
Assign via Enterprise Application → Users and groups
It's easy to build every other piece correctly and forget this step — the symptom looks like a "stuck" client-side auth flow, when it's really an unassigned role.
4 · Claude Code Side

.mcp.json — pointing Claude Code at APIM

{
  "mcpServers": {
    "apim-mcp-pipedrive": {
      "type": "http",
      "url": "https://mikes-apim.azure-api.net/pipedrive-mcp-server/mcp",
      "headers": { "Ocp-Apim-Subscription-Key": "[Subscription-Key-Here]" },
      "oauth": {
        "clientId": "[App-Reg-Client-ID-Here]",
        "callbackPort": 8080,
        "authServerMetadataUrl": "https://mikes-apim.azure-api.net/oauth-proxy/.well-known/openid-configuration",
        "scopes": "openid offline_access api://[App-Reg-Client-ID-Here]/user_impersonation"
      }
    }
    // Other MCP servers would go here — same app registration, same oauth-proxy
  }
}
callbackPort: 8080 must match the http://localhost:8080/callback redirect URI registered in Entra — Claude Code runs a loopback listener on that port during interactive login (/mcp).
5 & 6 · APIM Policies

Token validation at two layers, on purpose

API layer (pipedrive-api)
Rejects requests with no bearer token before touching validate-azure-ad-token
Validates audience + required roles claim, logs userId/userName/scope to App Insights
Strips the Authorization header before forwarding to the backend
Honoured even for callers that hit the API directly, not via MCP
MCP layer (pipedrive-mcp-server)
Same validate-azure-ad-token shape, deliberately duplicated
Lets the MCP surface require a different claim, or stay Entra-secured even if the underlying API's auth changes later
Tools exposed by the MCP server are picked from the API's operations in the APIM MCP configuration screen, then this policy is attached at the MCP layer.

Practical Takeaways

What to get right the first time

The wildcard discovery API is written once and serves every MCP server on the APIM instance — no per-server copy needed
Mark the app registration as a public client and register redirect URIs under Mobile and desktop applications, not SPA or Web
Assigning the app role in the Enterprise Application is a separate step from creating it — skip it and the failure looks like a client-side auth bug
Never log request/response bodies in the token proxy beyond a one-off debug trace — they carry live authorization codes and tokens; delete the trace the moment it's confirmed working
