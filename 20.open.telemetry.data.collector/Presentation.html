The Problem

Why monitor AI usage from VS Code?

No visibility by default
GitHub Copilot and Claude Code consume tokens every time you use AI features in VS Code
Out of the box there is no central record of how many tokens are being used, by whom, or for what
Cost and quota risk
Token consumption directly drives cost in pay-per-use models
Without measurement you cannot optimise, forecast, or set guardrails
No standard tooling
VS Code AI extensions do not natively ship telemetry to Application Insights or any central store
You need a lightweight local bridge to capture and forward that data
Goal: monitor, manage, and optimise token utilisation across your development team — starting with a single dev machine, scalable to an entire organisation.

Setup · Step 1

Install the OpenTelemetry Collector Contrib

Use the contrib distribution — it bundles the Azure Monitor exporter out of the box. Run this command to download and install the Windows service:

# Download and install the OTel Collector Contrib MSI
msiexec /i "https://github.com/open-telemetry/opentelemetry-collector-releases/releases/download/v0.157.0/otelcol-contrib_0.157.0_windows_x64.msi"
The installer registers a Windows service called OpenTelemetry Collector Contrib and installs config files under C:\Program Files\OpenTelemetry Collector Contrib\
Why contrib?
The standard distribution does not include the Azure Monitor exporter
The contrib build bundles every community exporter, including azuremonitor

Setup · Step 2

Configure config.yaml — add the Azure Monitor exporter

Edit C:\Program Files\OpenTelemetry Collector Contrib\config.yaml and add the exporter and pipeline entries:

Add the exporter
exporters:
  azuremonitor:
    connection_string: "InstrumentationKey=<KEY>;IngestionEndpoint=https://<region>.in.applicationinsights.azure.com/;LiveEndpoint=https://<region>.livediagnostics.monitor.azure.com/"
    maxbatchsize: 1024
    maxbatchinterval: 10s
    spaneventsenabled: false
Wire it into pipelines
pipelines:

  traces:
    receivers: [otlp, jaeger, zipkin]
    processors: [batch]
    exporters: [azuremonitor]

  metrics:
    receivers: [otlp, prometheus]
    processors: [batch]
    exporters: [azuremonitor]

  logs:
    receivers: [otlp]
    processors: [batch]
    exporters: [azuremonitor]
Tip: comment out or remove the debug exporter to avoid flooding the Windows Event Viewer.
Setup · Steps 3 & 4

Restart the service & configure VS Code

Step 3 — Restart the Windows service
Open services.msc
Find OpenTelemetry Collector Contrib
Click Restart — the new config.yaml is loaded on startup
Don't skip this step — the service reads config once at start; changes are ignored while running
Step 4 — Configure VS Code AI extensions
In VS Code settings, enable OpenTelemetry export for GitHub Copilot and/or Claude Code
Point each extension at http://localhost:4318 (OTLP/HTTP) or localhost:4317 (OTLP/gRPC)
From this point every AI feature invocation sends a local HTTP call to the collector Windows service
The collector listens on localhost only — telemetry never leaves the machine until the Azure Monitor exporter forwards it. There is no external exposure.
Setup · Verify

Verify the Azure Monitor exporter is active

The collector exposes a Prometheus-format metrics endpoint at:

http://127.0.0.1:8888/metrics

Open that URL in a browser. Look for azuremonitor in the output — if it appears, the exporter is registered and running.

Health check
Extensions endpoint: http://127.0.0.1:55679/debug/extensions
zpages trace viewer: http://127.0.0.1:55679/debug/tracez
pprof profiling
Available at http://127.0.0.1:1777/debug/pprof
Useful if the collector process is consuming unexpected CPU
Application Insights check
Open App Insights → Transaction Search
Trigger a Copilot or Claude Code action in VS Code
Events should appear within ~30 seconds
Application Insights

Where your data lands in Application Insights

Table What it contains Typical use
dependencies Each LLM call as a dependency span — model, duration, status Latency analysis, failure rates, per-model breakdown
traces Log messages emitted during AI operations Debug context, prompt/response content (if sensitive data enabled)
customMetrics Token counts — gen_ai.client.token.usage (input, output, total) Token consumption over time, cost modelling, quota alerts
customEvents Higher-level agent events if emitted by the extension Feature usage patterns, session analysis
The customMetrics table is the primary source for token utilisation reporting. Join it with dependencies on operation_Id to correlate usage with specific model calls.
Visualisation

Query & visualise with KQL

Once data is in Application Insights you can write KQL queries and publish them to any of these dashboard tools:

Azure Workbooks
Native to Application Insights — no extra setup
Rich chart types, time-range pickers, parameter filters
Share via Azure RBAC
Grafana
Use the Azure Monitor data source
Mix AI token metrics with infrastructure metrics on one board
Strong alerting integrations
Turbo360
Business-friendly dashboards on top of Azure Monitor
Good for executive token cost reporting
// Example: daily token usage by AI tool
customMetrics
| where name == "gen_ai.client.token.usage"
| summarize totalTokens = sum(value)
        by bin(timestamp, 1d),
           tool = tostring(customDimensions["gen_ai.system"])
| render columnchart
